## 🔐 Part 1: Security vs Privacy

### 1.1 ความหมายและความแตกต่าง

ผู้เรียนหลายคนมักสับสนว่า Security กับ Privacy คือสิ่งเดียวกัน — แต่ในความเป็นจริงทั้งสองมีมุมมองที่แตกต่างกันโดยพื้นฐาน

```
╔═══════════════════════════════════════════════════════════════════════╗
║             SECURITY  vs  PRIVACY — ไม่ใช่สิ่งเดียวกัน                      ║
╠═══════════════════════════════════════════════════════════════════════╣
║                                                                       ║
║  SECURITY (ความมั่นคงปลอดภัย)       PRIVACY (ความเป็นส่วนตัว)               ║
║  ┌───────────────────────────┐       ┌─────────────────────────────┐  ║
║  │ ปกป้อง: ระบบ & ข้อมูล        │       │ ควบคุม: ข้อมูลส่วนตัวของคน       │  ║
║  │ จาก: ผู้ไม่ได้รับอนุญาต         │       │ ว่าใครเข้าถึงได้บ้าง             │  ║
║  │ มุมมอง: ผู้ดูแลระบบ           │       │ มุมมอง: เจ้าของข้อมูล           │  ║
║  │ เครื่องมือ:                  │       │ เครื่องมือ:                    │  ║
║  │  Firewall, Auth,          │       │  Consent, Policy,           │  ║
║  │  Encryption, IDS          │       │  Anonymization, PDPA/GDPR   │  ║
║  └────────────┬──────────────┘       └──────────────┬──────────────┘  ║
║               │                                     │                 ║
║               ▼                                     ▼                 ║
║        ถามว่า: "ใครสามารถ                  ถามว่า: "เจ้าของข้อมูล          ║
║         เข้าถึงข้อมูลได้?"                    ต้องการให้ใครเห็น?"             ║
║                                                                       ║
║  ══════════════════════════════════════════════════════════════════   ║
║                   OVERLAP ที่สำคัญมาก                                    ║
║  ══════════════════════════════════════════════════════════════════   ║
║                                                                       ║
║  Security ดี ≠ Privacy ดี  │  Security ไม่ดี → Privacy ก็ไม่ดีด้วย            ║
║  Privacy ดี ≠ Security ดี  │  แต่ทั้งคู่จำเป็นต้องทำงานร่วมกัน                   ║
║                                                                       ║
║  ตัวอย่าง:                                                              ║
║  ❌ Encrypted DB แต่ขายข้อมูลให้ Data Broker  → Security ✓ Privacy ✗      ║
║  ❌ Privacy Policy ดีงาม แต่ DB ถูก Hack      → Privacy ✓ Security ✗     ║
║  ✅ เข้ารหัส + Consent ชัดเจน + Access Control → Security ✓ Privacy ✓    ║
╚═══════════════════════════════════════════════════════════════════════╝
```

### 1.2 ความสัมพันธ์กับ CIA Triad (ที่เรียนใน Week 1)

| มิติ | CIA Triad (Security) | Privacy Framework |
|------|---------------------|-------------------|
| **เป้าหมาย** | ปกป้องระบบและข้อมูล | ปกป้องสิทธิ์ของบุคคล |
| **Confidentiality** | เฉพาะผู้มีสิทธิ์เข้าถึงได้ | + เจ้าของข้อมูลควบคุมว่าใครมีสิทธิ์ |
| **Integrity** | ข้อมูลไม่ถูกแก้ไขโดยไม่ได้รับอนุญาต | + ข้อมูลต้องถูกต้อง เจ้าของขอแก้ไขได้ |
| **Availability** | ระบบพร้อมใช้งานเสมอ | + เจ้าของข้อมูลเข้าถึงข้อมูลตัวเองได้ |
| **เพิ่มเติม** | — | Collection Limitation, Purpose Limitation, Deletion Right |

> 💡 **สรุป:** Privacy คือ **"ส่วนขยาย"** ของ Confidentiality ในมุมมองของเจ้าของข้อมูล ไม่ใช่แค่ว่า "คนอื่นเข้าถึงไม่ได้" แต่รวมถึง "เจ้าของข้อมูลมีอำนาจควบคุมด้วย"

## 🇹🇭 Part 2: PDPA – พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562

### 2.1 ภาพรวม PDPA

**PDPA** ย่อมาจาก **Personal Data Protection Act** หรือ **พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562** มีผลบังคับใช้เต็มรูปแบบตั้งแต่ **1 มิถุนายน 2565**

```
│                                                                       │
```

### 2.2 ข้อมูลส่วนบุคคล (Personal Data) คืออะไร?

**ข้อมูลส่วนบุคคล** คือข้อมูลใดๆ ที่สามารถ **ระบุตัวตนบุคคลธรรมดาได้** ไม่ว่าทางตรงหรือทางอ้อม

| ประเภท | ตัวอย่าง | ระดับการป้องกัน |
|--------|---------|----------------|
| **ข้อมูลทั่วไป** | ชื่อ-นามสกุล, เบอร์โทร, Email, ที่อยู่, IP Address, วันเกิด, เลขบัตรประชาชน, Location data, พฤติกรรมออนไลน์ | ต้องมี Lawful Basis |
| **ข้อมูลอ่อนไหว (Sensitive Data)** | เชื้อชาติ/ศาสนา, ข้อมูลสุขภาพ, ประวัติอาชญากรรม, พฤติกรรมทางเพศ, ลายนิ้วมือ/Biometric, ข้อมูลพันธุกรรม, ความเชื่อทางการเมือง | ต้องขอ Explicit Consent + มาตรการพิเศษ |
| **ไม่ใช่ข้อมูลส่วนบุคคล** | ข้อมูลนิติบุคคล (บริษัท), ข้อมูลผู้เสียชีวิต, Anonymized data, Aggregated statistics | ไม่ต้องใช้ PDPA |

> ⚠️ **สำคัญ:** IP Address ถือเป็น Personal Data เพราะสามารถระบุตัวตนได้โดยอ้อมผ่าน ISP ดังนั้น Log file ที่เก็บ IP ก็ต้องมี Lawful Basis และ Retention Policy ด้วย

### 2.3 Lawful Basis — ฐานกฎหมาย 6 ประการ

ก่อนเก็บ/ใช้ข้อมูลส่วนบุคคล **ต้องมีฐานกฎหมายอย่างน้อย 1 ข้อ:**

```
┌─────┬──────────────────────┬──────────────────────────────────────────────┐
│  #  │    ฐานกฎหมาย         │   กรณีที่ใช้ในซอฟต์แวร์                            │
├─────┼──────────────────────┼──────────────────────────────────────────────┤
│  1  │ CONSENT              │ ❤️ Social app เก็บ preference, ส่ง newsletter  │
│     │ (ความยินยอม)          │    → ต้องขอชัดเจน เพิกถอนได้ง่าย                  │
├─────┼──────────────────────┼──────────────────────────────────────────────┤
│  2  │ CONTRACT             │ 📋 สมัครใช้บริการ → เก็บชื่อ/ที่อยู่เพื่อส่ง              │
│     │ (สัญญา)               │    สินค้า หรือออก Invoice                       │
├─────┼──────────────────────┼──────────────────────────────────────────────┤
│  3  │ LEGAL OBLIGATION     │ 📜 ธนาคาร/สถานพยาบาล ต้องเก็บตาม KYC/Tax       │
│     │ (พันธะตามกฎหมาย)      │    reporting                                 │
├─────┼──────────────────────┼──────────────────────────────────────────────┤
│  4  │ VITAL INTEREST       │ 🚨 ฉุกเฉินทางการแพทย์ แชร์ข้อมูลกู้ชีพ                │
│     │ (ชีวิตอันตราย)          │    (ใช้น้อยมากในทางปฏิบัติ)                       │
├─────┼──────────────────────┼──────────────────────────────────────────────┤
│  5  │ PUBLIC TASK          │ 🏛️ หน่วยงานรัฐ เก็บข้อมูลเพื่อสาธารณะ               │
│     │ (ภารกิจสาธารณะ)       │                                              │
├─────┼──────────────────────┼──────────────────────────────────────────────┤
│  6  │ LEGITIMATE INTEREST  │ 📊 Fraud prevention, Security log analysis   │
│     │ (ประโยชน์โดยชอบ)      │    → ต้องทำ Balancing Test ก่อนเสมอ            │
└─────┴──────────────────────┴──────────────────────────────────────────────┘
```

**💡 ตัวอย่างที่พบบ่อยในระบบ Registration:**
- เก็บ Email เพื่อสร้าง Account → ฐาน **Contract**
- ส่ง Newsletter → ต้องขอ **Consent** แยกต่างหาก
- วิเคราะห์พฤติกรรมผู้ใช้เพื่อป้องกัน Fraud → ฐาน **Legitimate Interest** (แต่ต้องทำ Balancing Test)

```
  │  โทษจำคุกสูงสุด 1 ปี                     │
  │  ค่าสินไหม 2 เท่าของความเสียหาย          │
  └──────────────────────────────────────┘
```

> 📌 **เปรียบเทียบ:** GDPR ก็กำหนด 72 ชั่วโมงเช่นกัน — นี่ไม่ใช่เรื่องบังเอิญ เพราะ PDPA ออกแบบโดยอ้างอิง GDPR เป็นหลัก

### 2.6 สิ่งที่ Developer ต้องทำใน Code

```python
# ❌ BAD: เก็บทุกอย่าง, ไม่ขอ Consent, ไม่มี Purpose
class UserRegistration(Model):
    username = CharField()
    email = CharField()
    phone = CharField()
    date_of_birth = DateField()
    address = TextField()
    gender = CharField()
    national_id = CharField()        # อันตราย! ไม่จำเป็นสำหรับ basic registration
    income = IntegerField()          # เกินความจำเป็น!
    # ... เก็บ 20 fields โดยไม่ถามว่าทำไม

# ✅ GOOD: Privacy by Design + PDPA Compliant
class UserRegistration(Model):
    # เก็บเฉพาะที่จำเป็น (Data Minimisation)
    username = CharField(max_length=50)
    email = EmailField(unique=True)
    password_hash = CharField()      # ห้าม plaintext เด็ดขาด!

    # Consent Management — บันทึกหลักฐาน
    consent_terms = BooleanField(default=False)      # required
    consent_marketing = BooleanField(default=False)  # optional, opt-IN
    consent_analytics = BooleanField(default=False)  # optional, opt-IN
    consent_timestamp = DateTimeField(auto_now_add=True)
    consent_ip = GenericIPAddressField()             # บันทึก evidence
    consent_version = CharField(default="v1.0")     # version ของ policy

    # Data Retention
    created_at = DateTimeField(auto_now_add=True)
    account_deleted_at = DateTimeField(null=True)    # soft delete

# Data Subject Request — ลบข้อมูล
def handle_deletion_request(user_id):
    user = User.objects.get(id=user_id)
    # Anonymize ไม่ใช่แค่ลบ (รักษา referential integrity)
    user.email = f"deleted_{user_id}@anon.invalid"
    user.username = f"deleted_user_{user_id}"
    user.account_deleted_at = timezone.now()
    user.save()
    # บันทึก Audit log
    AuditLog.create(
        action="USER_DELETION_REQUEST",
        user_id=user_id,
        timestamp=timezone.now()
    )
```

**Checklist สำหรับ Developer:**
- [ ] บันทึก Timestamp + IP ของ Consent ไว้ใน Database
- [ ] สร้างฟังก์ชัน "เพิกถอน Consent" ที่ทำงานจริง ไม่ใช่แค่ UI
- [ ] ทำ Data Retention Policy — ลบข้อมูลเมื่อหมดอายุ
- [ ] ทำ Audit Log ว่าใครเข้าถึงข้อมูลใด เมื่อใด
- [ ] มีระบบ Data Subject Request (DSR) ให้ผู้ใช้ขอดู/ลบข้อมูล
- [ ] เข้ารหัสข้อมูล Sensitive ทั้งใน Storage และ Transit

## 🇪🇺 Part 3: GDPR & เปรียบเทียบกับ PDPA

### 3.1 GDPR คืออะไร?

**GDPR** (General Data Protection Regulation) มีผลบังคับใช้ในสหภาพยุโรปตั้งแต่ปี 2018 ถือเป็น "Gold Standard" ของกฎหมาย Privacy ที่หลายประเทศทั่วโลกอ้างอิง รวมถึง PDPA ของไทย

```
╔═══════════════════════════════════════════════════════════════════╗
║   ❓ ทำไมต้องเรียน GDPR ทั้งๆ ที่เป็น EU Law?                            ║
╠═══════════════════════════════════════════════════════════════════╣
║                                                                   ║
║  1. Extraterritorial Effect: ถ้าระบบของเราให้บริการหรือเก็บข้อมูล        ║
║     ของคน EU แม้แต่คนเดียว — GDPR ใช้บังคับกับเรา                        ║
║     ตัวอย่าง: e-commerce ขายสินค้าให้นักท่องเที่ยว EU → GDPR!              ║
║                                                                   ║
║  2. Best Practice: GDPR มีบทบัญญัติที่ละเอียดและชัดเจนกว่า PDPA            ║
║     การออกแบบให้ comply GDPR จะครอบ PDPA โดยอัตโนมัติ                 ║
║                                                                   ║
║  3. Career: บริษัทข้ามชาติมักต้องการ Engineer ที่เข้าใจ GDPR               ║
║                                                                   ║
╚═══════════════════════════════════════════════════════════════════╝
```

### 3.2 เปรียบเทียบ PDPA (TH) vs GDPR (EU)

| ประเด็น | PDPA 🇹🇭 | GDPR 🇪🇺 |
|--------|---------|---------|
| **บังคับใช้เต็มรูปแบบ** | 1 มิ.ย. 2565 | 25 พ.ค. 2561 |
| **Lawful Bases** | 6 ฐาน | 6 ฐาน (ต้นแบบ) |
| **โทษปรับสูงสุด** | 5 ล้านบาท | 20 ล้านยูโร หรือ 4% ของรายได้ทั่วโลก |
| **Data Breach Notification** | 72 ชั่วโมง | 72 ชั่วโมง |
| **DPO (Data Protection Officer)** | บางกรณี | บังคับในกรณีที่กำหนด |
| **Right to be Forgotten** | มี (ม.33) | มี (Art. 17) |
| **Data Portability** | มี (ม.35) | มี (Art. 20) |
| **Privacy Impact Assessment** | สำหรับ High Risk | DPIA บังคับสำหรับ High Risk |
| **Extraterritorial Effect** | บางส่วน | กว้างมาก |
| **Consent Age** | ต่ำกว่า 20 ปี ต้องผู้ปกครองยินยอม | ต่ำกว่า 16 ปี (แตกต่างตาม Member State) |

### 3.3 GDPR 7 หลักการ (Seven Principles)

```
┌─────┬────────────────────────────────────────────────────────────────┐
│  1  │ LAWFULNESS, FAIRNESS, TRANSPARENCY                             │
│     │ เก็บอย่างถูกกฎหมาย, ยุติธรรม, โปร่งใส                                │
├─────┼────────────────────────────────────────────────────────────────┤
│  2  │ PURPOSE LIMITATION                                             │
│     │ ใช้ตามวัตถุประสงค์ที่แจ้งไว้เท่านั้น ห้ามเบี่ยงเบน                           │
├─────┼────────────────────────────────────────────────────────────────┤
│  3  │ DATA MINIMISATION                                              │
│     │ เก็บน้อย เก็บเฉพาะที่จำเป็นสำหรับวัตถุประสงค์นั้น                          │
├─────┼────────────────────────────────────────────────────────────────┤
│  4  │ ACCURACY                                                       │
│     │ ข้อมูลต้องถูกต้องและทันสมัย ต้องมีระบบให้แก้ไขได้                          │
├─────┼────────────────────────────────────────────────────────────────┤
│  5  │ STORAGE LIMITATION                                             │
│     │ เก็บนานเท่าที่จำเป็น กำหนด Retention Period แล้วลบ                   │
├─────┼────────────────────────────────────────────────────────────────┤
│  6  │ INTEGRITY & CONFIDENTIALITY                                    │
│     │ รักษาความปลอดภัย ป้องกันการรั่วไหล เข้ารหัสข้อมูล                        │
├─────┼────────────────────────────────────────────────────────────────┤
│  7  │ ACCOUNTABILITY                                                 │
│     │ พิสูจน์ได้ว่าทำตามกฎ (เอกสาร, Audit Log, หลักฐาน)                    │

```

> 📌 **ข้อ 7: Accountability** นี้สำคัญมาก — ไม่ใช่แค่ "ทำถูก" แต่ต้อง "พิสูจน์ได้ว่าทำถูก" ซึ่งหมายถึงต้องมีเอกสาร, Log, และหลักฐานการปฏิบัติตาม

## 🏗️ Part 4: Privacy by Design

### 4.1 แนวคิดและความเป็นมา

**Privacy by Design** คิดค้นโดย **Dr. Ann Cavoukian** ในปี 1990s และถูกบรรจุเข้าสู่ GDPR เป็น Legal Requirement (Article 25) แนวคิดคือ:

> *"Privacy ต้องถูกออกแบบเข้าไปใน System ตั้งแต่แรก ไม่ใช่ add-on ที่ติดมาทีหลัง"*

เปรียบได้กับการ **ออกแบบบ้านให้มีทางหนีไฟตั้งแต่ต้น** ดีกว่า **เจาะผนังเพิ่มทางหนีไฟทีหลัง**

### 4.3 Dark Patterns vs Privacy-Friendly Design

**Dark Pattern** คือการออกแบบ UX ที่ "ล่อหลอก" ให้ผู้ใช้แบ่งปันข้อมูลมากกว่าที่ต้องการ — ผิดกฎหมาย GDPR อย่างชัดเจน และ PDPA มีแนวโน้มตีความเช่นเดียวกัน

| Dark Pattern | คำอธิบาย | ตัวอย่างจริง |
|-------------|---------|------------|
| **Roach Motel** | สมัครง่าย ยกเลิกยากมาก | ต้องโทรหา Call Center เพื่อยกเลิก Netflix |
| **Confirmshaming** | ทำให้รู้สึกผิดถ้าปฏิเสธ | "ไม่ขอบคุณ ฉันไม่ต้องการประหยัดเงิน" |
| **Pre-ticked Boxes** | ติ๊กถูกไว้ให้แล้ว | ✓ รับข่าวสาร (ต้องยกเลิกเอง) |
| **Privacy Zuckering** | ทำให้แชร์มากกว่าที่ตั้งใจ | Facebook ตั้งค่า default = Public |
| **Hidden Opt-out** | ปุ่ม Unsubscribe เล็กมาก/ซ่อน | Link สีเทาเล็กๆ ที่ท้าย email |
| **Disguised Ads** | โฆษณาหน้าตาเหมือน Content | "ผลการค้นหา" ที่จริงคือโฆษณา |

**✅ Privacy-Friendly Patterns ที่ควรทำ:**
- Just-in-time Consent — ขอ permission ตอนที่ต้องใช้จริงๆ
- Granular Control — เลือกได้ละเอียด ไม่ใช่ all-or-nothing
- Easy Data Export / Account Deletion
- Privacy Dashboard ที่เข้าถึงได้ง่ายจาก Settings

```
│                                                                     │
│  Q5: ถ้าเป็นข้อมูลของแม่เรา เราโอเคไหม?                                  │
│      └─ Personal Stake Test — ไม่โอเค → ต้องเปลี่ยน                     │
│                                                                     │
│  ═══════════════════════════════════════════════════════════════    │
│  ตอบ "ไม่" แม้แต่คำถามเดียว → หยุดและหาทางออกที่ดีกว่า                       │
└─────────────────────────────────────────────────────────────────────┘
```

### 5.3 ประเด็น Ethics ที่พบบ่อยในวงการ Tech

#### 5.3.1 Location Tracking

**ปัญหา:** แอปเก็บ location ตลอดเวลาแม้ปิดแอปแล้ว และขาย location data ให้ third party

**กรณีจริง:**
- Google ถูกร้องเรียนโดย 40 รัฐในสหรัฐว่าติดตาม location แม้ผู้ใช้ปิด Location History แล้ว และจ่ายค่าปรับ 391.5 ล้านเหรียญ (2022)
- แอปหลายตัวส่งข้อมูล location ไปให้ data broker ซึ่งขายต่อให้บริษัทประกัน

**Best Practice:**
```
✅ ขอ permission เฉพาะ "เวลาใช้งาน" (While Using App)
✅ แจ้งชัดเจนว่าใช้ location ทำอะไร
✅ ไม่ขาย location ให้ third party โดยไม่บอก
✅ ลบ location history ตาม Retention Policy
```

#### 5.3.2 Behavioral Tracking & Profiling

**ปัญหา:** ติดตาม scroll, click, dwell time เพื่อ infer ข้อมูล sensitive ที่ผู้ใช้ไม่ได้ให้

**กรณีจริง:**
- **Facebook Emotional Manipulation Experiment (2014):** ทดลองจิตวิทยาบนผู้ใช้ 700,000 คนโดยไม่แจ้งล่วงหน้า เพื่อดูว่า feed ที่มี content เชิงลบ/บวกส่งผลต่ออารมณ์อย่างไร
- **Target & Pregnancy Prediction (2012):** วิเคราะห์ purchase history แล้วส่งโฆษณาสินค้าคนท้องให้วัยรุ่น ซึ่ง "พ่อไม่รู้ว่าลูกสาวท้อง"

**คำถามทางจริยธรรม:**
- ถ้า AI วิเคราะห์ข้อมูลสุขภาพแล้วบอก insurer ว่า "คนนี้เสี่ยงเป็นเบาหวาน" — ทำได้ไหม?
- การ infer ข้อมูล sensitive จากข้อมูลที่ผู้ใช้ให้มาโดยไม่รู้ตัว — ถือว่า consent หรือไม่?

#### 5.3.3 AI & Algorithmic Bias

**ปัญหา:** Training data ที่ bias → ผลลัพธ์ที่ discriminate กลุ่มคนบางกลุ่ม

**กรณีจริง:**
- **Amazon AI Hiring Tool (2018):** ระบบ AI สมัครงานปฏิเสธผู้สมัครเพศหญิงอัตโนมัติ เพราะ Training data ส่วนใหญ่เป็นข้อมูลพนักงานชาย
- **COMPAS Recidivism Algorithm:** ระบบทำนายโอกาสกลับมาก่ออาชญากรรม พบว่า bias ต่อคนผิวดำ ถูกใช้ตัดสินในศาลสหรัฐหลายรัฐ

**ข้อปฏิบัติ:**
```
✅ Audit Model สม่ำเสมอด้วย Fairness Metrics
✅ Diverse Training Data — ครอบคลุมทุกกลุ่ม
✅ Explainability — สามารถอธิบายการตัดสินใจของ AI ได้
✅ Human in the Loop — มีคนตรวจสอบการตัดสินใจที่มีผลกระทบสูง
```

### 5.4 ACM/IEEE Code of Ethics for Software Engineering

วิศวกรซอฟต์แวร์ควรยึดถือหลักการ 8 ข้อ (ย่อ):

| ข้อ | หลักการ | ความหมายในทางปฏิบัติ |
|----|---------|---------------------|
| 1 | **PUBLIC** | ผลประโยชน์สาธารณะมาก่อนผลกำไรบริษัท |
| 2 | **CLIENT & EMPLOYER** | ซื่อสัตย์ต่อลูกค้า แต่ไม่ทำสิ่งที่ขัดต่อจรรยาบรรณ |
| 3 | **PRODUCT** | รับผิดชอบต่อคุณภาพและความปลอดภัยของสิ่งที่สร้าง |
| 4 | **JUDGMENT** | รักษาความเป็นกลางในวิชาชีพ |

| 6 | **PROFESSION** | ยกระดับมาตรฐานวิชาชีพ |
| 7 | **COLLEAGUES** | ยุติธรรมและสนับสนุนเพื่อนร่วมงาน |
| 8 | **SELF** | พัฒนาตัวเองอย่างต่อเนื่อง |

## ❓ คำถาม-คำตอบ (Q&A)

**Q1: ถ้าแอปพลิเคชัน Mobile ที่เราพัฒนาต้องทำอะไรบ้างเพื่อ PDPA Compliance?**

A: ต้องทำอย่างน้อย 5 อย่าง:
1. **Privacy Policy** ที่อ่านได้จริง — ภาษาที่ชาวบ้านเข้าใจ ไม่ใช่ Legal jargon ยาว 10 หน้า
2. **Consent Management** — ขอ Permission ชัดเจนก่อนเก็บ ไม่ Pre-check ไว้ให้
3. **Data Minimization** — ขอ Permission เฉพาะที่จำเป็น
4. **User Rights Portal** — ให้ผู้ใช้ดูว่าเราเก็บอะไร และขอลบได้
5. **Secure Storage** — เข้ารหัสข้อมูล Sensitive ทั้ง at rest และ in transit

---

**Q2: ถ้า Log file ของ Server เก็บ IP Address — นับเป็น Personal Data ไหม?**

A: **นับเป็น Personal Data** ตามคำตีความของ PDPC และ GDPR เพราะ IP Address สามารถระบุตัวตนได้โดยอ้อมผ่าน ISP หรือ User Session ดังนั้น:
- ต้องมี Lawful Basis ในการเก็บ Log (โดยปกติใช้ฐาน Legitimate Interest)
- ต้องกำหนด Retention Period (เช่น 90 วัน)
- ต้อง Anonymize หรือลบ IP เมื่อหมด Retention Period

---

**Q3: ถ้าทำ Startup ไทยแต่ผู้ใช้อยู่ทั่วโลก ต้อง Comply กับกฎหมายอะไรบ้าง?**

A: ขึ้นอยู่กับว่า "Data Subject" อยู่ที่ไหน:
- ผู้ใช้ไทย → PDPA บังคับ
- ผู้ใช้ EU → GDPR บังคับ (แม้บริษัทอยู่ไทย)
- ผู้ใช้ California USA → CCPA บังคับ (ถ้ายอดรายได้ถึง threshold หรือมีผู้ใช้เยอะ)
- ผู้ใช้ Brazil → LGPD บังคับ

**ทางปฏิบัติ:** ออกแบบให้ comply GDPR ซึ่งเป็นมาตรฐานสูงสุด จะครอบกฎหมายอื่นส่วนใหญ่โดยอัตโนมัติ

---

**Q4: Privacy by Design กับ Security by Design ต่างกันอย่างไร?**

A: ทั้งสองมีปรัชญาเหมือนกันคือ "คิดตั้งแต่ต้น" แต่ต่างกันที่:

| | Security by Design | Privacy by Design |
|---|---|---|
| เน้นที่ | ปกป้องระบบจากภัยคุกคามภายนอก | สิทธิและความต้องการของ Data Subject |
| ตัวอย่าง | Threat Modeling, Input Validation, Encryption at rest | Consent Management, Data Minimisation, User Control |
| ถามว่า | "ใครสามารถโจมตีระบบ?" | "ผู้ใช้มีสิทธิ์ควบคุมอะไรได้บ้าง?" |

ในทางปฏิบัติ ควรทำทั้งสองไปพร้อมกันใน SDLC

## 🧪 Quiz 5 — ตัวอย่างข้อสอบ

**ข้อ 1 (ปรนัย):** บริษัทส่ง Newsletter โดยไม่ขอ Consent ก่อน แต่มีปุ่ม "Unsubscribe" — ถูกกฎหมาย PDPA ไหม?

ก. ถูก เพราะให้สิทธิ์ Unsubscribe แล้ว
ข. **ผิด เพราะ PDPA ใช้หลัก Opt-IN ไม่ใช่ Opt-OUT** ← คำตอบ
ค. ขึ้นอยู่กับว่าผู้ใช้เคยซื้อสินค้ากับเราหรือไม่
ง. ถูก ถ้า Privacy Policy บอกว่าจะส่งไว้แล้ว

---

**ข้อ 2 (ปรนัย):** ข้อใดคือหลักการสำคัญของ Privacy by Design?

ก. เพิ่ม Privacy feature หลัง Development เสร็จแล้ว
ข. ให้ผู้ใช้ต้อง Opt-OUT ถ้าไม่ต้องการแชร์ข้อมูล
ค. **Privacy ต้อง Embed ตั้งแต่แรก และ Default = ปกป้องสูงสุด** ← คำตอบ
ง. Privacy และ Security เป็น Trade-off กัน ต้องเลือกอย่างใดอย่างหนึ่ง

---

**ข้อ 3 (ปรนัย):** "Data Controller" ใน PDPA คือใคร?

ก. สำนักงาน PDPC ผู้บังคับใช้กฎหมาย
ข. Database Administrator ผู้ดูแลฐานข้อมูล
ค. **ผู้ที่กำหนดวัตถุประสงค์และวิธีการประมวลผลข้อมูล** ← คำตอบ
ง. เจ้าของข้อมูล (ผู้ใช้) ที่ให้ข้อมูลไป

---

**ข้อ 4 (อัตนัย):** อธิบาย "Dark Pattern" ในบริบทของ Privacy พร้อมยกตัวอย่าง 2 ตัวอย่าง และบอกว่าทำไมถึงขัดต่อหลัก Privacy by Design (5 คะแนน)

**แนวคำตอบ:**
- Dark Pattern คือการออกแบบ UI/UX ที่ตั้งใจทำให้ผู้ใช้แบ่งปันข้อมูลมากกว่าที่ต้องการ
- ตัวอย่าง 1: Pre-ticked checkbox "รับข่าวสาร" ที่ติ๊กไว้ให้แล้ว ผู้ใช้ต้องยกเลิกเอง
- ตัวอย่าง 2: Roach Motel — สมัคร newsletter ง่ายมาก แต่ยกเลิกต้องโทร Call Center
- ขัดต่อ Privacy by Design หลัก "Privacy as Default" (Default ต้องปกป้องสูงสุด) และ "Respect for User Privacy" (UX ต้องทำให้ Privacy choice ง่าย)

---

**ข้อ 5 (อัตนัย):** ระบุ Lawful Basis ที่เหมาะสมที่สุดสำหรับแต่ละกรณี (3 คะแนน):
1. แอปเรียกรถเก็บ Location ขณะผู้ใช้กำลังนั่งรถ → **Contract**
2. แอปส่ง Newsletter โปรโมชันประจำสัปดาห์ → **Consent**
3. ธนาคารวิเคราะห์ Transaction เพื่อตรวจจับ Fraud → **Legitimate Interest**

## 📋 Assignment: ฟอร์มสมัครสมาชิกฉบับปรับปรุง

**โจทย์:** ออกแบบ "หน้าฟอร์มสมัครสมาชิก" สำหรับระบบใดระบบหนึ่ง (เลือกเอง) ให้ PDPA Compliant และสอดคล้องกับ Privacy by Design

**สิ่งที่ต้องส่ง:**
1. **ฟอร์มสมัครสมาชิกฉบับปรับปรุง** (Mockup หรือ HTML/code จริง)
2. **เหตุผลการออกแบบ** ระบุสำหรับทุก field ว่า:
   - เก็บข้อมูลนี้ทำไม? → Lawful Basis ข้อไหน?
   - ทำไมถึงไม่เก็บ field บางอย่าง? → Data Minimisation
   - Consent mechanism ทำงานอย่างไร?
3. **Data Flow Diagram** (ใช้ draw.io template ที่แนบ) แสดงว่าข้อมูลไหลไปที่ไหนบ้าง
4. **User Rights Implementation** — ระบุว่าจะสร้าง feature อะไรเพื่อรองรับสิทธิ์ของผู้ใช้

**เกณฑ์การให้คะแนน:**
| เกณฑ์ | คะแนน |
|------|-------|
| Data Minimisation — เก็บเฉพาะที่จำเป็น + เหตุผล | 25% |
| Consent Mechanism — ถูกต้องตาม PDPA | 25% |
| Privacy Notice — ชัดเจน อ่านได้จริง | 20% |
| User Rights — ครบถ้วน ทำได้จริง | 20% |
| Data Flow Diagram — ถูกต้องและครบ | 10% |
